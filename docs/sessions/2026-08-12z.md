## The privacy-masking defect (worth reading)

Running the backend suite properly for the first time surfaced a **real intermittent failure** in
`privacy_masking.py`, roughly 1 run in 6. It had survived several sessions that reported "122 tests
pass" because it depends entirely on a random value.

`mask_text` substitutes identity/institution tokens into the text and *then* runs the structured
identifier patterns over the result — so the patterns also see the freshly-inserted tokens. The
namespace embeds a `secrets.token_hex(12)` nonce, and a hex nonce can contain a long digit run. When it
did, Phone (10 digits) or Card (15+) matched *inside* an already-emitted token and wrapped it in a
second token, which the deliberately single-pass rehumanizer cannot restore. The user saw raw `FTM_`
tokens instead of their own labels.

Fix: `_safe_nonce()` rejects any nonce matching a structured pattern. Underscore is not a valid
separator in those patterns, so a match can never cross the namespace boundary — screening the nonce
alone is sufficient. Bounded to 100 attempts (~1e-100 to exhaust) so a degenerate entropy source fails
closed rather than hanging a request. Verified by constructing an envelope with a known-bad nonce to
show the corruption, then 25 consecutive clean full-suite runs.

**Not a model leak** — the doubly-masked token still hid the real value from the model. It broke
restoration to the user, not confidentiality. Flagged rather than filed silently because it sits inside
D-133.

**Adjacent edge case left alone, deliberately:** the Card pattern could in principle match starting at a
token's trailing counter digit and run into following user text. Much rarer, and fixing it properly
means making the structured pass skip regions already occupied by tokens — a refactor of
privacy-critical code that should be a decision, not a drive-by.

## Simulator token strategy (D1)

Simulator screenshots are images and cost far more than text. Standing approach:

1. **Prove logic without it.** `node --test` for frontend, `unittest` for backend, `tsc --noEmit` for
   types. These are text, cheap, and catch most of what a screenshot would.
2. **Reserve the simulator for what is only observable at runtime** — layout, navigation, native
   permission prompts, anything that cannot be asserted in a test.
3. **Batch.** One build → one attach → walk several screens in a single session. Never relaunch per
   screen.
4. **Prefer `zoom` on a region over a full screenshot** when checking one detail.
5. **Do not attach the live panel** unless the owner wants to watch; verification is headless.
6. Do not open it at all for build-only, test-only, or backend-only work.

## Suspected defects found by the test-coverage pass — NOT fixed, awaiting owner

All are money/tax-shaped and hit the `CLAUDE.md` hard stop, so they were reported rather than changed.
See the audit doc and the session summary for detail. Highest first:

1. `tax_saving_room.py:52` — `unused_room` floors at 0 but is never clamped to the ₹1.5L cap, and
   `holding_fields.py` accepts negative numerics, so a negative contribution yields a user-facing room
   figure *above* the statutory cap. Tax-shaped.
2. `budget.py` — income cadence is not strict, unlike outflow cadence. A missing/unrecognised income
   frequency silently defaults to monthly, so fortnightly income is counted at ~46% of its value and
   `net` is wrong with no signal. This is the exact failure mode D-112 called unsafe on the other side
   of the same calculation.
3. `consolidated.py:53-58` — a product type outside the three family sets (e.g. `savings_balance`) is
   not counted, not excluded, and not statused; a user holding only that sees `"empty"`. Defeats the
   purpose of the valuation metadata.
4. `consolidated.py:67-83` — `float(c.get(...) or 0)` is unguarded, so an unparseable JSONB value 500s
   the whole response instead of marking one holding unvalued; `or 0` also conflates falsy-present
   with a real zero.
5. `esop_exercise_cost.py:106` — FMV exactly equal to strike takes the underwater branch and tells the
   user the strike is *above* FMV, which is false.
6. `esop_exercise_cost.py:27-31` — month-end grant dates lose a month, which can delay a cliff.
7. `esop_exercise_cost.py:97-100` — a zero-unit grant reads as "nothing has vested yet".
8. `streaks.py:49-54` — a future `last_active_date` (clock skew) resets the streak *and* writes the
   date backwards.
