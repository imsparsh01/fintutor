# BQ-061 — Portfolio category concentration

New: `app/lib/concentration.ts` (pure `computeCategoryConcentration`). Modified:
`app/screens/PortfolioScreen.tsx` — the card, plus that screen's first data fetch.

## Held to D-106's constraints deliberately

Counts only. The by-value version — "62% of your fund money is in equity" — was not built, because a
concentration share by value reads as a portfolio-weighting verdict rather than a fact about what you
hold, and that is the advice line. D-106 rules out a rupee figure here for exactly that reason.

Labelled "Category concentration", never "overlap". The D-091 block carries the load on this card: the
number is easy to mistake for an overlap measure, and the block is what says plainly that true
stock-level overlap needs scheme data the app does not have and does not fetch.

## Taxonomy gap found

D-106 names the categories "equity/debt/hybrid", but D-013's taxonomy has **no hybrid fund type** —
only `equity_mutual_fund` and `debt_mutual_fund`. Built against the two that exist.
`FUND_CATEGORIES` in `concentration.ts` is the single place to add a third if a hybrid type is ever
created. Flagging rather than inventing a category the rest of the app cannot record.

## Verification

Five render branches, all exercised in the web preview against a seeded synthetic dev user:
multi-category, single-category, single fund, no funds, and holdings-unavailable. The last two are
worth distinguishing — "you hold no funds" is a real answer and gets a D-089 teaching surface; "we
could not load your holdings" is not an answer and gets different wording with the D-091 block
omitted, since there is no number to caveat. `tsc --noEmit` clean.

Seeded holdings were created and then deleted through the API; the dev user is back to zero.

## Note for BQ-058

This adds the first `useFocusEffect` holdings fetch to PortfolioScreen. Safe today — PortfolioScreen
and HealthScoreScreen are never focused together, so there is no double-fetch on one focus event. It
does **not** settle the TODOS.md shared-store question, which is about health sub-scores diverging
between two surfaces, not about a holdings count.

# BQ-054 defect — "Tax utilisation" always scored 0

Not a queue item; an owner-directed fix of the first bug BQ-056 flagged below ("Bugs found outside
this task's scope"). One file changed: `app/lib/healthScore.ts`.

## What was wrong

Two independent mismatches, both shipped in BQ-054 (`d62f570`), each enough on its own to zero the row:

- `TAX_80C_TYPES = ['ppf', 'epf']` — neither is a real product type. D-013's taxonomy has the single
  value `'ppf_epf'`; PPF vs EPF is a `retirement_fund_type` characteristic, not a product type.
- The insurance branch read `characteristics.premium_annual`, which exists nowhere. The schema has
  `premium` plus a free-text `premium_frequency`.

`annual80C` therefore stayed 0 for every user whose holdings loaded, and the row rendered a confident
`0/100` rather than the user's real 80C utilisation.

## The part that needed the owner

The premium half looked like "invent a free-text normalisation", but it wasn't — `_to_monthly`
(`backend/app/services/budget.py:16`) already handles the vocabulary, and `tax_saving_room.py:43`
already computes this exact 80C quantity. The real question was narrower: **the two existing
precedents disagree** on a missing/unrecognised cadence. `tax_saving_room.py` reads it as monthly
(12x overstatement on an annual premium, pins the row at 100); `compute_budget` deliberately excludes
it ("Option C").

Escalated under the "calculations users rely on" hard stop. **Owner chose strict/Option C** →
**D-109 logged**. Reasoning in the decision file; the short version is that the failure modes aren't
symmetric — under-counting invites the user to look, a falsely-maxed row tells them to stop looking —
and `investmentRate` on the same screen already inherits Option C via `budget.recurring_outflows`.

## Accepted costs, both now in KNOWN_LIMITATIONS

1. The Health Score's 80C total and "Check my 80C room" **can disagree** for a holding with no stated
   cadence. Aligning them means changing a backend calculation — its own hard stop, out of scope here.
2. Half-yearly premiums are recognised for *display* (`HoldingDetailScreen.tsx:111`) but by no
   calculation. The recognised set mirrors `budget.py` exactly; adding a ÷6 on the frontend only would
   have created a second divergence while fixing the first.

## Verification

`npx tsc --noEmit` clean. Compiled the module and ran 23 runtime assertions against it — every cadence
and synonym, case/whitespace variance, missing/blank/unrecognised/non-string cadence, NaN and negative
guards, the ₹1.5L cap, `holdings === null` vs `[]`, and the combined PPF+premium shape. All pass.
Ran as a throwaway script: the repo still has no test runner, so none of this is committed as a
regression test. That is the notable gap in this fix.

Note for future sessions on this Mac: the worktree has no `node_modules`; `npx tsc` there resolves to a
decoy package and prints "This is not the tsc command you are looking for". Symlinking the main
checkout's `app/node_modules` into the worktree is enough to typecheck.

  `annual_contribution` reduce the 80C total. The new premium path guards against this; that line
  pre-dates the fix and was left alone rather than absorbed.
- ~~`HealthScoreScreen.tsx`'s "‹ Portfolio" back link still goes to Home.~~ **Fixed independently in
  `82b7956`** by the parallel session that shipped BQ-061 — noticed when rebasing onto it. Same
  `goBack()` bug BQ-056 hit on ScenarioScreen; now closed on all three hidden screens.
- **D-107's `/review` gate did not run as intended.** gstack now resolves, but `/review` dispatches to

# BQ-059 — Goals screen restructure

Replaced the `GoalsScreen` placeholder with the full layout D-106 specified. One file changed
(`app/screens/GoalsScreen.tsx`) — no new routes, no new lib files, no backend work.

Four sections: existing goal progress rows, four goal-type cards with an inline create form,
an insurance coverage summary, and an emergency readiness card.

## The illustration call (delegated to build time by the queue entry)

The four goal marks are drawn from plain `View`s — a rotated square plus a rule for the mortarboard,
three ascending bars, a CSS-triangle roof over bordered walls, two overlapping rings.
`react-native-svg` is not a dependency and adding one would be a hard stop, so no vector library was
introduced. The drawn-from-rules look also sits closer to D-086's warm-ledger register than clip-art
would have.

## Other decisions baked in

- **Goal creation reuses `createGoal` (D-038)** with `category` taken from the card the user tapped,
  so the form asks only for amount and date. This is a second entry point to an existing capability,
  not a new one. Goals are created unfunded; linking holdings to a goal stays BudgetingScreen's job.
- **One question, asked once.** Emergency readiness reads `hs_emergency_months` and health cover reads
  `hs_has_health_ins` — the same AsyncStorage keys HealthScoreScreen writes. The Goals screen never
  re-asks; it links back to the screen that owns the question.
- **P10 held throughout.** Goal progress is an ink fill on a `lineSoft` track, matching BudgetingScreen.
  `colors.danger` appears only on a rejected save, which is a genuine failure state per tokens.ts.
- **P2 held.** The insurance summary reports sum assured and a yes/no. It does not say whether cover is
  adequate, and the D-091 block says so outright.

## Verification

Ran both the backend and the Expo web preview. Created a real goal through the form and watched it
appear with a 0% progress track; confirmed validation rejects an empty save; entered 7.5 months on the
Health Score screen and confirmed the Goals emergency card picked it up on tab re-focus (the CTA also
flips from "Enter your buffer" to "Update the figure"). Goals → Scenario link confirmed. `tsc --noEmit`
clean. With the backend up, BQ-056's `from your data` prefill tags were also observable for the first
time and render correctly.

Note: verification created one goal row in the dev database under the synthetic dev-user id
`00000000-0000-0000-0000-000000000001`, not under the owner's user. `app/lib/goals.ts` exposes no
delete endpoint, so it was left in place — it is invisible to any real account.

## Known minor, not fixed

Arriving at the emergency-runway scenario from the Goals screen still shows a "‹ Tools" back link.
The label is honest about where the control goes (Tools is the scenario list's home), but the user
came from Goals. Left as-is rather than threading an origin param through the route.

## Key decisions baked in

- **The app never supplies a rate.** Expected return, inflation, savings rates are all user inputs.
  S-07 asks for two rates (what the cash earns now, what you're comparing against) rather than
  assuming cash earns nothing or that investments return 12%. This follows CalculatorScreen's
  existing behaviour, not a new rule — see D-108.
- **Prefills are editable and labelled** `from your data`, with a note saying where each came from.
- **RDs excluded from the FD total** — `principal_or_monthly_amount` is an instalment for an RD, and
  summing it as a balance would overstate emergency runway.
- **PPF/EPF included in runway** (D-106 names EPF) but the copy states the withdrawal restrictions
  and tells the user they can clear the field.
- **S-01 follows D-106's wording** (years/age to a user-set target), not BUILD_QUEUE's compressed
  "shows SIP needed" — which would have duplicated C-04.
- Each scenario carries a D-091 "what we won't say" block; all figures in `font.mono`/`colors.ink` (P10).
