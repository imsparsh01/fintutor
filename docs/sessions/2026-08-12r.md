Three real bugs were found and fixed during the run, not just failing assertions:

1. **Replay ordering depended on random UUIDs.** The tiebreak for events sharing an instant was `str(id)`,
   so two users taking the same actions in the same order could score differently depending on UUID luck.
   Now ordered by `(occurred_at, created_at, id)` — insertion order, and stable across replays.
2. **Pruning erased `last_event_at`.** Only raw events know the true instant, so a rebuild after pruning
   reset it to null. It is now preserved when replay has nothing newer to offer.
3. **A crowded day silently burned a once-ever award.** The derived idempotency key for once-per-subject
   events was lifetime-scoped, so an award blocked by the 60-point daily cap could never be earned again —
   the ledger refused the later attempt. Cap-subject once-ever keys are now day-scoped; the once-ever
   *award* is still enforced during replay. Cap-exempt milestones keep their lifetime key, so onboarding
   stays exactly `onboarding_handled:v{flow_version}` as D-121 specifies.

Also hardened: concurrent first events for a new user would both insert a summary row and one would 500.

## Judgment calls worth knowing about

- **`meaningful_return_day` is derived during replay, not recorded by callers.** It is a property of the
  day's own qualifying activity, so deriving it means it cannot be emitted spuriously or missed. Same
  points either way.
- **No partial awards under the daily cap.** An event that does not fit in the remaining budget does not
  award and does not consume its once-ever key, so the action earns full value on a later day. Partial
  credit would burn a once-per-subject award for a fraction of its worth.
- **`occurred_at` is not accepted from clients** — server clock only. A client-supplied instant would let
  a caller backdate across the Asia/Kolkata boundary and mint a fresh 60-point cap.
- **`lifetime_points` is not exposed by the API.** It can sit below the displayed high-water mark after a
  retune, and showing both would surface exactly the decrease the floor exists to hide.

## BQ-071 — partially shipped, one emitter blocked

Wired six of the seven buildable emitters. Backend: Arya exchanges on `/chat`, context prompts and
onboarding-handled on the assessment routes. Frontend: calculators and scenarios, plus capability-first-use
for each family, via a new `app/lib/progression.ts`.

Design points worth carrying:

- **Emitters are total, not just guarded.** `emit_safely` only wraps the write, but emitters also hash
  questions and read the clock outside it. A `@_never_raises` decorator now wraps each emitter whole. An
  API test that patched the emitter itself caught this — the original version would have propagated a
  pre-write failure straight into the route.
- **Emit last, after the host's writes commit.** The guard rolls back on failure, so it must have nothing
  of the caller's left to undo. `record_turn` and `handle_assessment` both commit before returning, so
  this holds today; the constraint is written into the codemap because it is easy to break later.
- **Arya keys on the question text for the day.** `/chat` is stateless with no turn id, and D-117 wants
  identical payloads deduped while reworded prompts may still qualify inside the 3/day cap. Case and
  surrounding whitespace do not make a question distinct.
- **Legacy onboarding turns are not Arya exchanges.** Onboarding earns its own one-time milestone;
  counting its turns as exchanges would double-reward the same flow.
- **Scenario emitters check for null.** Every compute function in `app/lib/scenarios.ts` returns null when
  it cannot produce an honest number, and those must not earn progress.

**Blocked: `teaching_moment_explored` and the teaching capability family.** Not a threshold question — a
direct collision between two standing decisions. D-117 needs the event to distinguish engaging from
opening-and-leaving; D-090's P9 guard forbids `TeachingWalkthrough` from reporting any value that
"differs from calling `onDismiss` early", and says an implementation missing that guard "is not a permitted
variant of `1f` — it is the lesson tree `PROJECT_SPEC.md` §2 and P9 forbid." The component header
explicitly says a feature wanting such a signal needs its own decision record. Escalated, not worked
around. Details in the BQ-071 queue entry.
