## Not shipped: the tax utilisation fix — superseded by D-109

Both sessions diagnosed the same two silent defects, identically:
`TAX_80C_TYPES` matching `'ppf'`/`'epf'` against a taxonomy whose value is the single type
`'ppf_epf'`, and a read of `characteristics.premium_annual`, which does not exist (the schema has
`premium` + free-text `premium_frequency`). Both degraded to 0 via `Number(undefined) || 0`.

Where the two diverged is the part that mattered. Annualising a premium whose cadence is missing
or unrecognised has **two disagreeing precedents already in the backend**:

- `tax_saving_room.py` calls `_to_monthly` bare, so a blank cadence reads as monthly.
- `compute_budget` applies "Option C" — an amount with no recognised cadence is excluded entirely.

I read this as already-decided and ported `tax_saving_room.py`'s lenient behaviour, on the grounds
that it is literally the app's 80C calculation. That was the wrong call. The parallel session
recognised it as a live question, escalated it under the "calculations users rely on" hard stop, and
the owner confirmed **D-109**: follow the strict Option C reading and exclude the premium, accepting
that the app's two 80C figures can now disagree. The reasoning is asymmetric failure modes — a score
that is too low invites the user to look; a falsely maxed one tells them to stop looking. That is a
better answer than mine, and it is owner-confirmed, so it stands.

**Lesson worth keeping:** "an existing implementation exists, therefore the policy is decided" is not
sound when two existing implementations disagree. Two conflicting precedents is itself the signal to
escalate, not licence to pick one.

## Flagged for the owner — still open, NOT covered by D-109

**Tax regime is never asked, so 80C is scored for new-regime users too.**
`tax_saving_room.py` handles this explicitly — new regime returns `applicable: false` with a note
saying 80C mostly doesn't apply. The Health Score has no regime input, so it scores every user on 80C
utilisation and averages that into the overall score. Before the defect was fixed this was moot
(everyone scored 0); it is live now on both sides of the merge. `docs/KNOWN_LIMITATIONS.md` does not
mention it. Options: ask the regime, drop `taxUtil` for new-regime users, or accept it. Tax-shaped
and product-shaped, so it is an owner call, not a build task.
