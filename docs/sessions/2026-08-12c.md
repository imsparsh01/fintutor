## The bug

`computeSubScores`'s taxUtil returned 0 for every user, always. Two independent field-name
errors, both silent:

- `TAX_80C_TYPES = ['ppf', 'epf']` — the D-013 taxonomy value is the single type `'ppf_epf'`
  (`app/lib/taxonomy.ts`). No holding is or ever was `'ppf'` or `'epf'`, so the branch never fired.
  Confirmed by grep: every other reader in the repo, frontend and backend, uses `'ppf_epf'`.
- `characteristics.premium_annual` — no such field. `characteristicsSchema.ts` defines `premium`
  plus a free-text `premium_frequency` for both `term_insurance` and `endowment_ulip`.

Because `Number(undefined) || 0` is 0, both failures degraded to "0% of your 80C cap used"
rather than to an error or a null, so nothing surfaced them.

## The annualisation question was already answered

The earlier log flagged "how to annualise from free-text `premium_frequency`" as needing an owner
call. It doesn't — the app already has a decided 80C definition in
`backend/app/services/tax_saving_room.py` (BRIEF-016/D-070), which does
`_to_monthly(premium, premium_frequency) * 12`. So this was a port, not a new policy, and no
decision was logged.

`annualisedPremium()` in `healthScore.ts` mirrors that exactly, including the default: an
unrecognised or blank frequency reads as already-monthly. Note that this deliberately follows
`tax_saving_room.py` and **not** `compute_budget`'s Option C, which instead drops an outflow whose
frequency is unrecognised. The two backend behaviours already differ; the 80C figure is the one
this screen is reporting, so it follows the 80C one.

Also replaced the bare `150000` with a named `ANNUAL_80C_CAP` matching the backend's
`_ANNUAL_80C_CAP`.

## Flagged for the owner — not decided here

1. **Tax regime is not asked, and 80C largely doesn't apply under the new regime.**
   `tax_saving_room.py` handles this explicitly — new regime returns `applicable: false` with a
   note. The Health Score has no regime input, so it now scores every user on 80C utilisation and
   averages that into the overall score. For a new-regime user that sub-score is arguably
   meaningless and drags the average down. Before this fix the point was moot (everyone got 0);
   it is live now. Options: ask the regime, drop taxUtil for new-regime users, or leave it. Product
   + tax-shaped, so it's an owner call.
2. **80C is now computed in two places.** `TaxSavingRoomModal` renders the backend's figure;
   `healthScore.ts` recomputes the same quantity client-side. They agree in definition as of this
   commit, and `docs/CODEMAPS/frontend.md` now says so under "Key patterns" — but it is duplicated
   money logic across two languages and will drift if only one side is edited. Consolidating means
   either making `computeSubScores` async against the backend route (which also needs the regime
   input from item 1) or moving the whole score server-side. Not attempted here.
3. **No unit tests exist for `app/lib/`.** The fixture run above was done through a throwaway script
   in the scratchpad, not committed, because adding a test runner would be a new dependency —
   a hard stop. `healthScore.ts` and `scenarios.ts` are both pure and both compute figures users
   read; they are the obvious first candidates if a runner is ever approved.
